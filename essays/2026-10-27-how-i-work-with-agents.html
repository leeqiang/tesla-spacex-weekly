我如何与 Agent 协作：Thorsten Ball「How I work with Agents (as of October 2026)」精读

说明：这是阅读笔记 / 精读摘要，不是全文翻译。观点归原作者所有，建议对照原文阅读。

原文链接：X 原帖（Thorsten Ball @thorstenball）

Thorsten Ball 在 Amp 每天和编码 Agent 一起工作。这篇是他截至 2026 年 10 月的工作方式快照，一共 15 条。

1. 用最新最强的模型

便宜或旧的模型看着省钱，其实浪费时间：它的输出可能 90% 是对的，但你不知道错的是哪 10%，结果只能逐行检查。最强的模型才值得你信任，也才能真的放手。

2. 别过度担心 slop

「Agent 写出来的代码是垃圾、没法维护」，这话六个月前也许成立。现在作者不再相信 Agent 一定会让代码库变得无法维护。

3. 提示里写 What，不写 How

描述你要的终态，而不是步骤。比如「把这个字节码编译器 / VM 尽可能优化，直到快 2 倍为止」。目标和验收标准讲清楚，路径交给 Agent 去找。

4. 让整个 SDLC 对 Agent 可见

工具调用能压住幻觉：Agent 能自己去查真实情况，就不用靠猜。它应该能跑端到端测试、看生产日志、部署、灰度发布、发版、开关 feature flag、做 triage，甚至给客户发邮件。原则是：你能看到的东西，Agent 也应该能看到。

5. 给它 SDLC 工具

光有权限不够，还要有趁手的工具。可以写自定义插件：读 bug 报告、给用户发邮件、「系统现在健康吗？」、操作 feature flag 等。

6. 用实验检验知识有没有被用上

AGENTS.md、skills、各种文档会越堆越多，可它们真的被用上了吗？做实验：同时开两个互不知情的 Agent，对照组不给这份知识，实验组给，然后比较结果，看它到底有没有用、有没有被用。

7. 本地跑多个 Agent 很别扭

每个 Agent 都需要能自由安装依赖、启动服务。放在远端环境里很容易，在本地就很难受：端口、数据库、资源都会互相冲突。

8. 别跟 Agent 来回试错，让它自建迭代工具

不要一轮轮手动调。可以让它一次生成 20 个变体，再做一个测试页面并排对比；排查问题时，让它先提出 4 种假设，然后把四种都验证一遍。

9. 要铁证

不要相信「我已经修好了」。要的是证据：操作演示、demo 视频、改动前后的数字。还可以在 AGENTS.md 里写明哪些东西「不算证据」。

10. 别等 Agent，让 Agent 等你

异步工作：给它更大、更有野心的任务，成批交代，不要一来一回地聊。也不要执着于首 token 延迟（TTFT），反正你又不在旁边盯着。

11. 自动化、定时、唤醒、心跳是杀手锏

「两小时后去查一下日志」「上线了告诉我」「每天早上 9 点做一遍」。能定时唤醒、自己跟进的 Agent，价值会高出一个量级。

12. 别手动管理上下文

上下文压缩（compaction）已经好用了。规则很简单：一个线程只做一个任务。线程可长可短，46 条消息可以，3714 条也可以。

13. 线程就是公司的记忆

在 Amp 里，线程会和 git commit 关联。以后有人（或者 Agent）能追溯某处改动当时的思路和讨论，也能避免把同样的活再干一遍。

14. 少写给人看的文案

大多数写给人看的说明文字可以省掉。例外是调试步骤、事故报告，以及一些机械性的文档。

15. 只审高爆炸半径的代码

只亲自审查影响面大的部分，比如那不到 5 个最核心的文件；数据库迁移要审。代码风格、类型、命名、重复代码可以不审，前提是：它能用，有端到端测试，能在架构图的层面看懂，并且一个月后还能改得动。

---

一句话总结：用最强的模型，给它看到并操作整个开发流程的能力，用目标和证据而不是步骤和信任来管理它，然后异步地放手。
